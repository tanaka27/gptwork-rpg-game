# 配信画像の軽量化（元画像は変更しない）

- 状態：反映完了（GitHubのみ、Sites未反映）
- 設計版：v1
- 要求・背景：画像が無駄に重くないかの調査で、起動時に背景2枚を読み込むこと、写真に近い背景と表示より大きな顔画像を lossless WebP で配信していることが分かった。元画像に手を加えずに、ブラウザが取得する容量を減らす（ユーザー要望）。
- 設計作成者：Claude Code

## 調査結果
- 開発サーバーで起動直後の画像取得は約8.8MB（PC/スマホ相当とも）。本番（lossless WebP）でも約5.8MBと見積もり。
- `index.html` が村の背景を先読みしており、草原から始めても村と草原の両方を取得していた。
- 背景は1448×1086、本番で1枚約2.2〜2.5MB。表示はPCで最大852px幅、スマホで370px幅。
- 初期4人の顔は512×512で1枚400〜500KB。表示は54〜104px。
- 本番Worker（画像を埋め込む）のgzipは約9.0MBで、上限10MBの約90%を使っていた。
- Gitの履歴に古い画像は残っておらず、リポジトリの容量は問題なし。

## 実装設計
- A：背景の先読み（`<link rel="preload">`）を削除。背景は表示する場面で読み込む。
- 方法1：`scripts/image-delivery.cjs` に配信用の変換規則を置き、`scripts/build.cjs` が該当PNGだけを縮小・非可逆圧縮する。背景2枚は解像度を保って品質80、初期4人の顔は320px（最大表示104pxの約3倍）に縮小して品質85。それ以外は従来どおり lossless。規則の対象のPNGがなければビルドを止める。
- URL・ゲーム側のコード・元画像は変更しない。開発サーバーとE2Eは元のPNGを配信する。
- `qa:worker-assets`：規則の対象は、大きさ・原本とのPSNR 30dB以上・PNGの4分の1以下の容量を確認。ほかは画素同一性を確認（従来どおり）。

## 実装・検証結果
- 見た目：libwebp（Pillow）で品質80/85に変換し、背景は等倍の切り抜き、顔は208px表示で元画像と並べて目視。違いは見分けられなかった。サイズは村372KB・草原284KB・顔16〜25KB。
- ビルド：この環境のImageMagickは6（本番ビルドは7が必要）。版の確認だけを外した一時実行で、変換・埋め込み・`qa:worker-assets` が成功した。Worker gzipは9.0MB→3.7MB。ImageMagick 6は WebP の `-quality` を反映しなかった（品質指定なしの既定値で変換された）ため、ImageMagick 7 での最終的なサイズと画質は未確認。Codexの公開時のビルドで確認する。
- 起動時の取得：先読みの削除で村の背景を取得しなくなり、開発サーバーで8.8MB→5.2MB（元のPNG）。本番は約0.5MB（草原・顔4枚・魔物）の見込み。
- `npm test` 成功。全E2E 144/144成功（PC/スマホ相当幅、管理画面PC/スマホ）。iOS/Android実機は未確認。
- 作業中に、計測用サーバーを止めるコマンドがE2E用のサーバー（管理画面スマホ幅）も止めてしまい、1回目の全E2Eで管理画面スマホ幅が失敗した。原因は自分の操作で、サーバーを残して全件を実行し直した。
