# 戦闘メッセージ送りのテスト不安定と同名の敵の区別

- 状態：反映完了（GitHubのみ、Sites未反映）
- 設計版：v1
- 要求・背景：`battle-flow.spec.cjs:91` がまれに失敗する問題を根本解決したい（ユーザー要望）。
- 設計作成者：Claude Code

## 目的・受け入れ条件
- 戦闘メッセージを送ったかの判定が、乱数で同じ文が続いても失敗しない。
- 同じ名前の敵を、画面・攻撃対象の選択・メッセージで区別できる。

## 原因調査
- 該当テストを120回繰り返すと6回失敗（PC/スマホ相当とも）。すべてEnterで送った直後の判定。
- 表示したメッセージを記録する調査用テスト80回で、同じ文が続いた5回とも、メッセージは1件進んでいた。2体の「リーフジェリー」が続けて同じ味方へ同じダメージを与え、同じ文が2回続いていた。
- テストは `#latestLog` の文が変わったことで「送った」と判定しており、同じ文が続くと失敗する。同じ判定がほかに6か所あった。
- 通常戦は「抽選した1体＋魔物表の先頭3種」の編成で、抽選が先頭3種と重なると同じ名前の敵が並ぶ（約3/4の戦闘）。同じ名前の敵は画面でもメッセージでも区別できなかった。

## 実装設計
- A：メッセージを1件出すたびに通し番号を増やし、`#fieldMessage` の `data-message-seq` に出す。テストは「番号が増えた、または待機中のメッセージがなくなった」で送ったことを判定する（`party-helpers.cjs` の `messageSeq`・`expectMessageAdvanced`）。自動送りのテストは自動送りの最短間隔（0.9秒）より短い時間で判定する。文の比較で判定していた7か所を置き換え。
- B：同じ名前の敵に、隊列順でA・B…を付ける（`labelDuplicateEnemies`、`battleEnemies()` で毎回適用・冪等）。元の名前は `baseName` に残す。出現のログも同じ名前にそろえる。画像・ドロップ・図鑑はIDで判定しているため影響なし。
- 互換性：セーブ形式は変更なし（敵の `name` と任意の `baseName`）。記号のない戦闘中の旧セーブにも読み込み時に付ける。
- 対象外：編成の偏り（先頭3種の固定）の見直し。

## 検証計画
- 変更した7か所を含むE2E、同名の敵の新規E2E、全E2E。`battle-flow.spec.cjs:91` を多数回繰り返して失敗しないことを確認する。
