# 設計・レビュー・承認の手順

## 適用範囲

ユーザーの要求に基づくすべての実装に適用します。小規模な修正、UI・データ変更、リファクタリングも対象です。文書のみの整備は対象外ですが、実装を伴う場合は必ずこの手順を通します。

調査・設計書作成・実装・テスト・必要文書更新は指定のサブエージェント（以下「子」）が担当し、親エージェント（以下「親」）が設計と実装結果をレビュー・承認します。これにより設計作成者とレビュー担当を分けます。親は実装コードを直接書かず、修正が必要なら指摘を子へ返します。

親が子を起動する際は `fork_turns=none`、`model=gpt-6-luna`、`reasoning_effort=max` を明示し、要求、対象範囲、関連仕様、受け入れ条件、制約など必要なコンテキストを渡します。この割り当てはコード変更だけでなく文書更新を委任する場合にも適用します。指定モデルまたはeffortが使えないときは別のモデル・effortに変更せず、阻害要因を報告します。ユーザーへの都度の設計・実装承認確認は不要です。

## 進め方

1. **調査・設計（子）**：要求、既存仕様、影響範囲を確認し、`docs/plans/YYYY-MM-DD-短い識別名.md` に設計書を作成します。同日の別案件は識別名を分け、版番号を付けます。既存の `docs/DESIGN.md` はUI指針であり、案件ごとの設計書の代わりにはなりません。
2. **設計レビュー（親）**：親は要求の充足、変更範囲、互換性・保存データ、異常系、検証可能性を確認し、識別子、日時（日本時間）、対象版、判定、指摘、対応を記録します。指摘があれば子が設計書を修正し、親が更新版を再レビューします。阻害指摘がなくなるまで繰り返します。
3. **設計承認（親）**：親は阻害指摘を解消した最終版を明示的に承認し、識別子、日時（日本時間）、対象版、実際の承認結果・条件を記録します。承認を推測・捏造せず、条件付き承認の条件が未充足なら実装しません。親は設計作成者ではないため、作成者とレビュー担当が分離されます。ユーザーによる設計書レビュー・承認は不要です。
4. **構築・検証（子）**：子は承認された設計の対象範囲・受け入れ条件に沿って実装と検証を行い、関連Markdownと変更履歴を更新します。各条件に対応する結果、設計との差異、未検証事項を設計書に追記します。動作変更時のPlaywrightなど必要な検証は[開発手順](DEVELOPMENT.md)と[AGENTS.md](../AGENTS.md)に従います。
5. **実装レビュー・承認（親）**：親は実装結果と検証記録をレビューし、必要に応じて独立した検証を行います。親はコードを直接修正せず、指摘を子へ返します。子が修正と再検証を行い、親が再レビュー・承認します。
6. **反映（親）**：親は実装結果の承認後にGit commit/pushと既存Sitesへの反映を行い、成功を確認します。ユーザーがその作業で反映不要と指定した場合は従います。作業ごとの許可確認は不要です。
7. **変更管理**：設計の範囲・仕様・方式に変更が必要なら、該当実装を止め、子が版を上げて差分・理由を記載します。親の再レビューと更新版の再承認後に再開します。過去のレビュー・承認は対象版とともに履歴として残します。

設計承認前は読み取り調査、設計書作成・修正、レビューのみを進めます。実装コード・実装用テスト・生成物の変更、本番データの更新は行いません。子は承認済み設計の対象版を確認してから実装します。親は対象版への承認を明記します。文書のみの変更は実装ゲート対象外ですが、文書更新を子へ委任する場合も指定モデルとeffortを使い、親が内容をレビューします。

push・デプロイの継続的な事前承認は設計・実装のレビューを代替しません。親による実装結果の承認と検証が済めば、公開の都度確認は不要です。push・Sites反映は親が行います。
