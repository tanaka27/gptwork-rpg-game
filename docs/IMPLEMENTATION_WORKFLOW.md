# 設計・レビュー・承認の手順

実装の親子分担、必須モデル、push・Sites反映、動作変更時の検証ルールは[AGENTS.md](../AGENTS.md)が正本です。この文書は実装前の設計承認に必要な手順だけを定めます。

## 適用範囲

機能追加、バグ修正、UI・データ変更、リファクタリングなど、実装コードを変更する作業に適用します。文書のみの整備は対象外です。文書以外も変更することになった場合、その実装はこの承認フローを通します。

## 設計と実装

1. 子エージェントが要求、仕様、影響範囲を調査し、`docs/plans/YYYY-MM-DD-短い識別名.md` に設計書を作成します。画面デザイン指針の `docs/DESIGN.md` は案件設計書の代わりにはなりません。
2. 親エージェントが設計の要求充足、範囲、互換性、異常系、検証計画をレビューし、識別子、日本時間の日時、対象版、判定、指摘・対応を設計書へ記録します。
3. 指摘を解消した対象版を親が明示的に承認してから、子が実装と検証を始めます。承認には識別子、日本時間の日時、対象版、実際の結果と条件を記録します。承認を推測・捏造せず、条件付き承認の条件が未充足なら実装しません。承認前に実装コード、実装用テスト、生成物、本番データを変更しません。
4. 設計の範囲・仕様・方式に変更が必要になったら、該当実装を止め、設計書の版を上げます。親が更新版を再レビュー・再承認してから再開します。以前の別版への承認を流用しません。
5. 子が承認済み設計に沿って実装・検証し、結果と未検証事項を記録します。親が差分と検証結果をレビューし、指摘があれば子が修正・再検証します。レビュー・承認の対象版を残し、反映と復旧の方法を案件設計書に記載します。レビューが通った後の反映はAGENTS.mdの役割分担に従います。

## 設計書テンプレート

案件ごとに複製し、未確定事項を解消してレビューを依頼します。実在しないレビュー・承認を記入しないでください。

- 状態：設計中 / レビュー中 / 承認待ち / 承認済み / 実装中 / 検証済み / 反映完了
- 設計版：v1
- 要求・背景：
- 設計作成者（子）：

## 目的・受け入れ条件
- 要求ごとの期待結果：

## 対象範囲
- 変更するファイル・機能：
- 影響する既存仕様・関連文書：
- 対象外：

## 実装設計
- 処理・画面・データ・APIの変更内容：
- 既存セーブ・公開済み定義との互換性と移行：
- 異常系・境界条件・リスクと対策：

## 検証計画
- 各受け入れ条件の確認方法：
- 必要なロジック/API/Playwright検証：
- 対象外の検証と理由：
- 反映・復旧方法：

## 親エージェントの設計レビュー記録
- 識別子・日時（日本時間）・対象版：
- 判定：未実施
- 指摘・対応・再レビュー結果：

## 親エージェントの設計承認記録
- 状態：未承認
- 識別子・日時（日本時間）・対象版：
- 承認結果・条件：

## 設計変更履歴
- 版・変更理由・レビュー・承認の参照：

## 実装・検証結果
- 受け入れ条件と結果の対応：
- 設計との差異・未検証事項：
- 子の実装・検証記録：
- 親の実装レビュー・承認記録：
- push・デプロイ結果の参照：
