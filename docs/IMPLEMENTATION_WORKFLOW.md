# 設計・レビュー・承認の手順

## 適用範囲

ユーザーの要求に基づくすべての実装に適用します。小規模な修正、UI・データ変更、リファクタリングも対象です。文書のみの整備は対象外ですが、実装を伴う場合は必ずこの手順を通します。

## 進め方

1. **調査・設計**：要求、既存仕様、影響範囲を確認し、`docs/plans/YYYY-MM-DD-短い識別名.md` に設計書を作成します。同日の別案件は識別名を分け、版番号を付けます。既存の `docs/DESIGN.md` はUI指針であり、案件ごとの設計書の代わりにはなりません。
2. **別エージェントレビュー**：設計作成者と異なるエージェントへ、要求・設計書・関連仕様を渡します。要求の充足、変更範囲、互換性・保存データ、異常系、検証可能性を確認し、レビュアーの識別子、対象版、判定、指摘、対応を記録します。実装は依頼しません。指摘を修正した場合は更新版の再レビューを受け、阻害指摘がなくなるまで繰り返します。別エージェントが使えない場合は代替承認せず、阻害要因を報告します。
3. **別エージェントの承認**：阻害指摘を解消した最終版について、レビュー担当エージェントが明示的に承認します。承認者の識別子、日時（日本時間）、対象版、実際の承認結果を記録します。承認を推測・捏造せず、条件付き承認の条件が未充足なら実装しません。ユーザーによる設計書レビュー・承認は不要で、エージェントの承認後はそのまま実装へ進めます。
4. **構築・検証**：承認された設計の対象範囲・受け入れ条件に沿って実装します。各条件に対応する検証結果、実装との差異、未検証事項を同じ設計書に追記します。動作変更時のPlaywright、Markdown更新、GitHubへのpush、既存Sitesへのデプロイは[開発手順](DEVELOPMENT.md)と[AGENTS.md](../AGENTS.md)に従います。
5. **変更管理**：設計の範囲・仕様・方式に変更が必要なら、該当実装を止め、版を上げて差分・理由を記載します。別エージェントの再レビューと更新版への別エージェント再承認後に再開します。過去のレビュー・承認は対象版とともに履歴として残します。

承認前は読み取り調査、設計書作成・修正、レビューのみを進めます。実装コード・実装用テスト・生成物の変更、本番データの更新は行いません。サブエージェントは自由に利用できますが、すべての実装担当にこのゲートと承認済み設計の版を共有します。レビュー時に対象版への承認を明記し、設計作成者が自己承認しないでください。

push・デプロイの継続的な事前承認は設計承認を代替しません。承認済み実装の検証が済めば、公開の都度確認は不要です。
