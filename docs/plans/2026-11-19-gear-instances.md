# 装備の個体化とレアリティ抽選（ハクスラ型）

- 状態：設計中（段階1。数値と下記「確認事項」のユーザー確認待ち）
- 設計版：v1
- 要求・背景：同じ装備でもレア版があるように、ドロップした装備ごとにレアリティと追加効果を抽選したい（ユーザー要望）。
- 設計作成者：Claude Code

## 目的・受け入れ条件
- ドロップした装備は1本ずつレアリティと追加効果を持つ。同じ装備を複数本持てる。
- 月蝕のローブ・星灯りの剣は固有装備としてレアリティと効果を固定のまま残す。
- ショップは今と同じ固定品を売る。基礎補正と装備Lvは装備定義ごとに固定。
- 既存セーブの能力値・装着状態・進行は移行後も変わらない。

## 対象範囲と段階
| 段階 | 内容 | 遊びの変化 |
| --- | --- | --- |
| 1 | この設計書の確定 | なし |
| 2 | 所持品の個体化、旧セーブの移行、セーブ検証 | なし（全個体が今の固定値） |
| 3 | ドロップ時の抽選と抽選ルールの定義・検証 | あり |
| 4 | もちものの個体一覧、並べ替え、装着中との比較、売却、所持上限 | あり |
| 5 | 管理画面での抽選ルール編集、数値調整 | あり |

- 段階ごとに設計書の該当節を詳しくし、実装・検証・pushする。
- 対象外：基礎補正の抽選、装備の強化・合成、消耗品の個体化。

## 実装設計

### 定義（`content/game.json`）
- 装備定義の `rarity` / `bonusEffects` は「標準品」（ショップ品・初期装備・移行時）の値として残す。
- 固有装備に `unique: true` を追加（`eclipse_robe`、`starlight_blade`）。固有装備は抽選せず常に標準品。
- 抽選ルール `rules.gearRoll` を追加（段階3）。旧公開定義にない場合は、`withJobs` で同梱定義の値を補う（装備レベル `level` と同じ方式）。
  - `rarityRates`：コモン70%、アンコモン22%、レア7%、レジェンダリー1%（合計100%）。
  - `statRates`：能力ごとの装備Lv1あたりの係数。最大HP 1.5、攻撃力・賢さ・うんのよさ 0.35、守備力・素早さ 0.3。
  - `rarityRanges`：倍率の幅。アンコモン0.5〜0.8、レア0.6〜0.9、レジェンダリー0.7〜1.0。
  - 追加効果は能力6種から重複なしに、アンコモン1・レア2・レジェンダリー3個を選ぶ。数値は `max(1, round(係数 × 装備Lv × 倍率))`。
  - 例：星銀のつるぎ（Lv10）のレジェンダリーでも攻撃+4・素早さ+3・うんのよさ+4が上限で、星灯りの剣（攻撃+5・素早さ+4・うんのよさ+6）を超えない。

### セーブ（キー `starlight-rpg-v1`・形式 `v:2` のまま、任意項目の追加）
- `gear: [{uid, baseId, rarity, bonusEffects}]`：所持品の正本。`uid` は1以上の整数で一意。
- `nextGearUid`：次に振る `uid`。
- 主人公の `weaponUid` / `armorUid`、仲間の `companions[].weaponUid` / `armorUid`：装着中の個体。
- **1つの個体を装着できるのは1人だけ**。今は同じ装備IDを全員で共有して装着できるが、個体化後は1人1本になる。
- 従来の `owned`・`weapon`・`armor`・`companions[].weapon/armor` は、保存のたびに個体から再計算する写し（装備IDの一覧と装着中の装備ID）として残す。これで以前の版に戻しても、そのセーブを読める（追加効果は標準品の値になる）。
- 能力計算（`GameRules.stats`）は個体の `rarity` / `bonusEffects` を使う。個体がない旧形式では今と同じく定義から計算する。

### 旧セーブの移行（読み込み時、非破壊）
- `gear` がなければ、装着中の装備を1人につき1個体ずつ作り、残りの `owned` の装備も1個体ずつ作る。値はすべて標準品。
- 例：全員が旅人の剣を装着中の新規セーブは、旅人の剣4本と旅人の服4着になる。
- 新規開始も同じく、4人分の初期装備8個体で始める。
- 移行で能力値が変わらないことをロジックテストで保証する。移行に失敗したら元のデータを保持し、進行を消さない。

### 検証（`shared/save.js`）
- `uid` の重複、未知の `baseId`、`rarity` と効果の個数の不一致、効果の能力・数値の範囲（抽選の上限以内。固有装備と標準品は定義値と一致）を拒否する。
- 装着中の `uid` が `gear` に存在し、部位が合い、同じ個体を2人が装着していないことを確認する。写しが個体と矛盾したら拒否する。
- 公開定義の切替時も、既存セーブの `baseId` 参照を検証する。

### 段階3・4の要点
- ドロップ：確率13%と候補一覧は今のまま。候補がベース装備なら抽選し、固有装備なら標準品。所持済みでも星のしずくにせず、新しい個体として加える。
- 所持上限：装着していない個体は30本まで。満杯のときのドロップは、星のしずく1個に置き換える（メッセージで知らせる）。
- 売却：街でだけ、装着していない個体を売れる。価格は `floor(基準額 × レアリティ倍率)`。基準額は「ショップ価格の半分」、価格0の装備は「装備Lv × 10」。倍率はコモン1・アンコモン1.5・レア2.5・レジェンダリー5。
- 戦闘後の報告と装備詳細に、個体のレアリティと抽選された効果を表示する。今のレアリティ枠はそのまま使う。

## 異常系・リスク
- 個体化で、装備を参照する約17か所（装着、ショップ、能力計算、詳細表示、クラウド保存、公開検証）が影響を受ける。段階2はここだけを扱い、挙動が変わらないことを既存のE2E全件で確認する。
- 改ざんされたセーブや壊れたセーブは検証で拒否する。読み込み時の正規化でも、壊れた個体は標準品に戻す。
- 戦闘中の定義スナップショット（`battleContent`）に `rules.gearRoll` も含める。

## 検証計画
- ロジック：移行（旧 `v:1`・旧 `v:2`・共有装着）、能力値の不変、検証の正常系と負例、抽選の確率と上限（乱数を差し替え）。
- API：クラウド保存・復元で個体を保持し、不正な個体を拒否する。
- Playwright：もちもの・ショップ・キャラクター詳細・戦闘後のドロップを、PC幅とスマホ相当幅の両方で確認する。段階2では全E2E。
- 反映・復旧：段階ごとにmainへpushする。写しを残すので、commitのrevertでも既存セーブを読める。
